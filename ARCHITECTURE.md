# Architecture

detent is the desktop's Settings app: one window on Blitz, drawn only with quire's components.
Programs ship a schema of their settings (quire design/22 section 9); detent renders pages from
every schema it finds and reads and writes the files the schemas name. It does not talk to a
program about a setting: each program's own directory watch applies what detent writes. The one
word it sends is the person's, to memory, for a setting looser than the shipped one. CONVENTIONS.md holds the
rules every repo shares; this file is detent's map and rules, and wins where they disagree.

### The fence

`detent-ui` names only `detent-client` (the one door to the computer), `detent-model` (the facts, and
`detent_model::external`: the ids and enums of porter, docket, almanac and chordkit that the facts
are made of, plus `toml::Value`, named once there) and quire. Its `[dependencies]` cannot name
`detent-files`, `detent-system`, `porter-*`, `almanac-*`, `docket-*` or `zbus`, so a view cannot
read a file or call a service; `scripts/check-boundary.sh` enforces it (`DIRECT`, and the exact
`EDGES` row). What a view needs from the files is `detent-client`: the settings, agents, places and
keymap files and the style and program scans are re-exported or wrapped there (`files.rs`), and the
work that blocks (the assistants' download, the program scan, the style files) is a `Client`
command that runs on a blocking thread.

All text a person reads is in `detent-ui/src/copy/<pane>.rs`: the model and the client return facts
(enums, ids), never a sentence of the window's own (a service's own words travel as they came).
`copy/common.rs` holds the buttons several panes share. `detent-intents` speaks to the assistant,
not the window, so its few lines about accounts (`src/accounts.rs`) stay its own words.

### Stand-in services in a test jail

The desktop's test jail has neither `/etc/quire/desktop-callers.toml` nor systemd units, and a
stand-in built in a checkout is an image its author can write, which peephole never calls a service.
So Settings, which judges its peers only against that table, would call every daemon a stranger.
The `detent` binary has a cargo feature `dev-callers` (off by default; the desktop harness builds
with `--features dev-callers`) that turns on `detent-callers/dev-callers` and so peephole's
`dev-rows`, and adds `detent --dev-callers FILE`:

- The file is the person's own rows (`[[peer]]` with `app`, `role` and `exe`, for example
  `app = "org.quire.Accounts"`, `role = "accounts"`, `exe = ["<the stand-in's image>"]`): a plain file
  (a link is refused) of this user or root that group and others cannot write.
  `detent_callers::use_dev_rows` reads it once at start (`crates/detent/src/dev_callers.rs`), before
  any peers exist; a file that cannot be read ends the start with a failure and one line.
- `desktop_peers` merges the rows after the shipped table, so a row never takes a unit the shipped
  table names, and a program they name is a service at `Proof::Dev`, below every real proof.
- Every question that requires a role lists its ways in through `detent_callers::allowing`: the
  role at the proof a unit gives, and in a `dev-callers` build also the role at `Proof::Dev`. That
  covers the owner of each daemon's bus name (`RoleCheck`: accountd, syncd, inferd, the
  compositor and the others) and the callers of Settings' own door (`detent-intents/src/callers.rs`).
  A release build lists the real proof alone and has no option, no `rustix`, no `thiserror` and no
  `dev-rows`.
- Not a security boundary: the person's own file says who is a service. The same list also lets in the
  real service at any proof, which a test build wants.

## 3. Recipes

**A key kind gets a component.** Add the `Control` variant in `detent-model/src/control.rs` (the
match on `KeyKind` is total, so the compiler lists what is missing), add `controls/<name>.rs` in
`detent-ui` with one quire component, and one arm in `controls/mod.rs`.

**Help is on request.** A row's `help` shows behind its ⓘ button (`help_shown: HelpShown::OnRequest`, with a stable `common.id` from `key_row::row_id` where the path is known). Inline stays for the first-run window (the words are its content) and for rows whose help is an error or a live state: the unavailable-service rows, "None" local models, an account's expiry, an outside assistant's sign-in line, a lending guest's standing.

**Advanced keys.** A page's advanced keys are not drawn on the page. Each advanced section is one row
("Limits..."; named by `detent-model::advanced_name`: the section's title, unless a basic section of the page has that title, then the one key's label or "<Title> Details") in the page's last group (`detent-ui/src/advanced_view.rs`); the row opens a quire
`Sheet` titled with the section, holding its rows with the same controls. Edits write live and the
sheet's one Done button (Return) closes it. A search hit marks the section's row; it opens nothing.

**A page appears.** Nothing to do: a program ships a schema naming the page, `Catalogue` groups it.
A new fixed page is a variant of `ds_settings::schema::Page` (quire first), then its slug in
`detent-model/src/page.rs` (its place in the sidebar is its row in quire's `pages.toml`) and an icon in `detent-ui/src/icons.rs`.

**An action is added.** Declare it in `dist/intents/org.quire.Settings.toml` (every field written,
a `params` list even when empty), add its arm in `detent-intents/src/ask.rs` and in
`SettingsProvider::perform`, and a test on the private bus (`detent-intents/tests`). Run
`../docket/scripts/check-intents.sh`; the installer (`scripts/install.sh`) already ships the file.

## 5. Repo rules

- Gate: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features -- -D
  warnings`, `cargo test --workspace`, `./scripts/check-boundary.sh`, `cargo deny check licenses`, and `./scripts/check-intents.sh` (docket's
  conformance check: a `.desktop` file needs a valid manifest; it builds `docket-eval` from `../docket`).
  Check every exit code.
- No `unsafe` anywhere (`unsafe_code = "deny"`).
- No widget is drawn locally. A kind quire has no component for is shown read-only with an "Edit in
  file" note and listed in FINDINGS.
- detent never removes anything: a save sets only the key the person changed, and every other key,
  known or not, keeps its text (only the owning program may drop what it does not read). A value a
  key's control cannot hold is shown read-only with "Edit in file". A schema whose `file` is not `<app>/<name>.toml` is stale and skipped.

## 6. App id and porter callers

detent's app id is `org.quire.Settings` (porter refuses a name that is not reverse-DNS), and
`dist/org.quire.Settings.desktop` is named after it, with `StartupWMClass` the same, so the window's
class matches its launcher entry. The porter daemons give it the Settings role by its unit, not by its name (sec-3): only the main
process of the user unit `org.quire.Settings.service` (`dist/systemd/org.quire.Settings.service`,
Type=dbus, BusName=org.quire.Settings, ExecStart=/usr/bin/detent --service) is Settings; the D-Bus service file
names it with `SystemdService=` so activation starts that unit, and `scripts/install.sh` puts both in
place. A detent started any other way (a terminal, an app scope) is an ordinary app with no Settings
role. porter's `dist/callers.toml` and `dist/inferd.toml` name the unit, which detent does not copy.

`dist/skills/settings/` is the companion's skill for this app (docket's skills format). Its `uses`
are `settings.key.read` and `settings.key.set` of the intents manifest, and its body lists the
agent-settable keys of design/22 section 9.7. Check it with
`docket-eval --check-skills <detent> <docket>`; the installer copies it to `share/quire/skills/settings/`.

## The look (style pass, 2026-10)

- The sidebar is `sidebar.rs` (pages in `sidebar_groups`, a `sidebar-gap` heading between groups, a coloured `TileFace` per page from `icons.rs`) with `person_card.rs` under the search field (`PersonCard`: reads `Client::whoami()` once; a press opens the Accounts page; drawn only when a person is known).
- A page is `page_view.rs` (`Level::Page` or `Level::Advanced(section)`), `page_body.rs` (the hero, the blocks, the advanced rows) and `advanced_view.rs` (one drill-in `Row` with a chevron per advanced section; a press shows that section's rows under quire's `PageHeader` with its back button). Overview pages (`PageKind::head`) open with `hero_view.rs`; its sentence is `copy/heroes.rs`.
- A row's grey line is the key's `note` (`key_row.rs`); `help` is search and assistant data and is not drawn. A slider shows `ends` at its two ends (`controls/slider.rs`), a section its schema `footnote` (`SectionModel::footnote`, from `ProgramSchema::footnotes`, drawn by `section_view.rs`). No row carries an info button.
- Nothing to show is `system::Absent` (a tile, one sentence, an action), never a greyed row; a page that opens with a hero leaves the tile and the name out. Tests address all of it by `data-page-row`, `data-person-card`, `data-hero`, `data-advanced-row` and `data-system="unavailable"` (`tests/ui/look.rs`).
